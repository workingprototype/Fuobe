# Architecture

Fuobe is a single Next.js 16 app. The browser (and the `fuobe` command line) talks only to Fuobe's own API; the server talks to providers (fal.ai, Replicate, ComfyUI, and Claude or Ollama for text), fetches LoRA files from Hugging Face and civitai when a run needs them, and stores every input and output locally, so the library never depends on a provider's expiring URLs. Since round 4 part 4 the admin decides which models, providers, licence classes, node packs and LoRAs the install offers (Settings → Models & licences; everything is on by default), and a read-only share link (`/s/<token>`) opens one page and its files without a session. Since round 4 part 5 Fuobe calls no Higgsfield API: Higgsfield is only what Fuobe is measured against, and a stored or scripted reference to one of its models runs on what replaced it (see Retired models). Since round 5 part 1 a feature gets a cloud route only where its model (or its base model, with LoRA support) is hosted on fal or Replicate; otherwise it runs on the open engine only, with no stand-in recipe (the owner's decision of 2026-10-29; see Fuobe Originals for the one exception, and two smaller cases, left to decide). A user skill can also carry a recipe that Fuobe checks, prices and runs by itself (see Skills that run by themselves).

A **model** has one **route** per (operation, provider). A route's `FieldMap` translates Fuobe's canonical input (`prompt`, `images`, `image2`, `endImage`, `video`, `videos`, `audio`, `audios`, `aspectRatio`, `duration`, `voice`, `voiceAudio`, `dialogue`, `shots`, `draft`, `startTime` / `endTime`, `fps`, `palette`, `styleId`, `numLayers`, `sourceLanguage`, `targetLanguage`…) to the provider's field names. Dotted keys (`voice_settings.stability`) are written as nested objects; `setPath` ignores `__proto__`, `constructor` and `prototype`. `defaults` are sent unless the request sets them (applied before the canonical fields), `fixed` always wins (applied after). `sourceLanguage` may be `{key, values}`, matched to the API's list. `palette {key, format, background}` converts hex colours to each API's shape (Recraft on fal's `{r,g,b}` objects, Ideogram members with falling weights, plain lists; an `rgb`-array format is still supported, unused since Higgsfield's Recraft route went). `tracks` and `timeline` build fal FFmpeg compose timelines. Masks are converted to each API's convention (white = change, black = change, or alpha) by a small PNG codec (`src/server/png.ts`).

## Providers (`src/server/providers/`)

Every adapter implements `isConfigured`, `prepareFile`, `submit` and `poll`, and optionally `cancel` and `test`. `RemoteOutput` carries optional `text` and `meta`. `prepareFile(data, type, name, route)` gets the route the file is for (ComfyUI sends an isolated-worker workflow's inputs to that worker). `test({ focus })` names the setting being checked, for a provider whose settings reach more than one server (the Anthropic key, the isolated worker's address).

- **fal** — queue API (`queue.fal.run/<endpoint>`); always uses the `status_url` / `response_url` returned at submit. Files go to fal storage via `@fal-ai/client`. The key test (15 s timeout) counts only 2xx, 400, 404 and 422 as "accepted"; a proxy or an outage (405, 407, 5xx) reads "Couldn't check the key". Since round 4 part 2, LoRAs go in the route's LoRA field (`routeLoraField`: one item per file, Wan 2.2's expert as `transformer`, `weight_name`, the scale clamped, at most the API's maximum) and the call switches to the route's `loraEndpoint` (`loraEndpointFor`; an endpoint that needs at least one LoRA is never called with none). `prepareFile` uploads a named `File`, so uploads keep their name and extension (a mirrored LoRA stays `.safetensors`).
- **replicate** — predictions API; small files as data URIs, larger via the Files API. Outputs are copied immediately (Replicate deletes them after an hour). Since round 4 part 2 it sends LoRAs (before, it ignored them): `lora_weights` / `lora_scales` arrays, one LoRA per Wan 2.2 expert, or one field, switching to the route's LoRA model when it has one (`loraEndpointFor`).
- **retired providers** (round 4 part 5). The Higgsfield adapter (`higgsfield.ts`) is gone, with its key, its key test and its live style lists (`GET /api/providers/higgsfield/presets`). - **comfyui** — loads `workflows/comfyui/manifest.json`. `prepareWorkflow()` turns a `GenInput` into the prompt: canonical keys → bindings, uploads it makes itself (including media refs in `params.extra`), LoRA nodes after each diffusion-model loader, width / height from aspect ratio + tier, frame counts as `n·step+1`, the palette as a hex sentence plus a 512×512 swatch rendered on the server, `SLOT_RULES` (repeat, required, hints) per workflow, and graph rewrites for `expand: "captions"` (`expandCaptionWorkflow` in `src/lib/comfy.ts`) and `expand: "timeline"` (`expandTimelineWorkflow` in `src/lib/av/timeline.ts`). ## Pipelines and chained jobs (`src/server/chains.ts`)

A generation can depend on others (`CreateOptions.dependsOn`, one id or a list). `GenerationRequest.chain` (`ChainSlot[]`) says where each dependency's output goes:

| slot | what it fills |
|---|---|
| `images` (first / last), `endImage`, `video`, `videos`, `audio` | the matching input, from the dependency's first output of that kind (an `audio` slot fed by a clip takes its soundtrack) |
| `voiceAudio` | the voice to clone (tts) or the target voice (voice change) |
| `audio2` | the second track mixed under `inputs.audio` (mux): `inputs.audio2` / `GenInput.audio2` |
| `audios` | a list of clips (the spoken lines a voice timeline places at their start times; the clips of an audio join) |
| `model3d` | a 3D model (a mesh to rig) |
| `mask` | what to change (remove-object): the output marked `meta.role` `mask` (the open painted eraser's last tracked frame, handed to the next window), else a mask video (SAM 3.1's track), else a still |
| `prompt` | the dependency's text: replaces `{text}` in the prompt, or becomes it; a translate step gets the cue list (decided by the step's planned op) |

An audio slot can carry `stem` to take the output whose `meta.stem` matches ("voice" also matches vocals / speech / target; "background" also accompaniment / instrumental / residual / no_vocals). `pickOutput()` in `generations.ts` does the choosing; a missing stem fails the step with a clear message. Since round 5 part 1 a slot can carry `raw: true`: it takes the picture as the model made it (`meta.original`), before Fuobe Soul's finish in the browser, so a look board's next frame is made from the previous one and every frame is graded once (`chainValue`, now exported).

**`createPipeline(steps, opts)`** creates any DAG of steps `{key, request, after?, chain?}`. Before a single row exists it checks duplicate or unknown keys, self-waits, loops (Kahn sort, linear in steps + edges, since a per-frame render has hundreds), chain-slot counts and output numbers (`index` / `of`), that a step others depend on makes one job, and previews every step with placeholders; a mix of demo and real steps is refused (`assertOneMode`). Rows are created in topological order with `dependsOn`, labelled "Step n of N", and it returns `{batchId, items, byKey}`; if creation fails partway, what it started is canceled. Since round 4 part 2, `opts.existing` maps keys to generations made before (a retry's finished or running steps): new steps may wait for them, they aren't made again, and a demo step can't continue steps that ran for real. Its TSDoc example is a whole dub. Layers, Shorts, Mixed Media, the palette lock, Photodump / Fashion / Character Sheet, the AI Influencer builder's two-step sheet, Marketing Studio / Click to Ad / Ad Multiplier, dub, Katana, Remove object, Genjutsu, the Audio hub's Loop / extend and Join, the Assist studio tools, and since round 5 part 1 Evolution, a skill's recipe (one pipeline per run or CSV row, and its dry run) and the PixeletedFace face mosaic (`createMosaicRun`) build their jobs this way; Cinema, Canvas, Faceless / Explainer, Content Factory's reading steps, Ads Studio and moodboards call `createGenerations` (with `dependsOn` for chained steps) directly (since round 4 part 3 Canvas uses `createPipeline` for a node made in steps or rows); Cinema, Canvas and Faceless preview every step first.

At launch the runner fills the slots (`slotsFor` pads short chains, `chainValue` reads text files when the text isn't inline) and checks the mode again (`chainMode`: a real step after demo steps runs as a demo, or fails with what to connect when demo mode is off). Round 4 part 2 changes the runner for every chain, for per-frame work:

- **Fan-out and fan-in by output number.** `ChainSlot.index` takes the dependency's output number i of the slot's kind (by `meta.index` when the outputs carry it; past the end, the last one). One step per index fans a list out (a step per extracted frame); one step with a slot per index gathers it back in order. With `of`, the number of outputs planned, a list more than `CHAIN_LIST_SLACK` (2) short fails the step before it runs (`listShortfall`), so a frame or two lost at the clip's end is held, and half a clip of frozen, paid frames is not.
- **Waiting steps are picked by readiness.** `advanceDependents` reads `READY_DEPENDENTS` (`generations.ts`): waiting rows none of whose inputs is still queued or running, or one of whose inputs failed, was canceled or is gone. Before, it read the 50 oldest waiting rows, so a render with hundreds of waiting steps held up every chain started after it. A step whose input failed is now failed at once, even behind a backlog.
- **`dropWhenUnused`.** A waiting step marked so (today only per-frame Mixed Media's frame edits and clips) is canceled unpaid ("Stopped before it ran: the steps it was for failed", `DROPPED_UNUSED`) once every step that would use it has failed or been canceled. `dropUnused` runs when a chained step fails and on cancel, and walks up the chain.
- **Retries.** A launched step is stored with `chainFilled: true`; `unfilledRequest()` takes the chained inputs out again, so a retry can rebuild the step from new or kept dependencies (Mixed Media's `retryMixed`, with `createPipeline`'s `existing`).
- **Optional inputs** (round 4 part 4, Genjutsu's anchor first frame). A `ChainSlot` marked `optional {prompt?, notice}` is an input the step can do without: when the step feeding it fails or is canceled, `advanceDependents` launches the step without that slot (`withoutSkipped`) instead of failing it, with the slot's fallback prompt, and records `chainSkipped` (the slots left out and the planned prompt). The `notice` is said on the result and carried down to every later step (`GenerationRequest.notice`). `unfilledRequest()` puts the planned prompt back, so a retry tries the full plan again. Chains without optional slots run as before; the runner now reads each dependency's stored request to gather notices.
- **Model access** (round 4 part 4). `createGenerations` checks the model with `offeredFor` before any step is queued, and `assertOneMode` (`chains.ts`) checks every step's model and routes against Settings → Models & licences, so a chain with a step switched off is refused, naming the switch, before a row exists. The chains built after the first row (`createShotFilm`, `createExtendChain`, `createRelitClip`, `joinClips`) cancel what they queued when a later step throws.
- **Waiting for ComfyUI** (round 4 part 5). Before it launches a step whose model runs on ComfyUI, `advanceDependents` reads the cached reachability (an Original counts with the routes of the engine it will run on, `pickEngine` with ComfyUI taken as answering, so a step on the cloud half doesn't wait). When ComfyUI doesn't answer and an earlier step ran on it for real, one missed check (a server busy finishing those steps, or restarting) mustn't turn this step into a demo, which `chainMode` would fail: the step looks again at once (one forced check per sweep), then stays queued with "Waits for ComfyUI to answer" for up to 60 s from the first miss (`COMFY_WAIT`; the first miss is kept in memory by step id) before `chainMode` has its say. The Canvas concatenator's join after its fit steps is such a step.
- **Demo dry runs** (round 5 part 1, Work2Skill W1). A request with the server-set `demo: true` runs on the demo provider whatever Settings → Demo mode says: `prepare()` passes it to `chooseRoute` (`forceDemo`), and `chainMode` lets a step after demo steps run as a demo with Demo mode off when it carries the flag. `joinClips`, `createShotFilm`, `createKeyframeFilm` and `createExtendChain` pass it on to the steps they add. The API drops the field from input (see Skills that run by themselves).

Built on that:

- **Join clips** (`joinClips`): fal's FFmpeg `merge-videos` on the cloud, ComfyUI's `video-concat-{2,3,4}` on the open engine (folded four at a time). `oss-join-sound1/2` are joins that keep one clip's own sound at 25 fps (marketing films). `oss-join-encoded` (`video-concat-encoded`, `expand: "videos"`) joins up to 100 clips in one prompt by packet copy when they share size and frame rate; Faceless Frame by frame films use it, 24 clips per join.
- **Open multi-shot** (`createShotFilm`), **storyboard film** (`createStoryboardFilm`; since round 5 part 1 it takes the film's shape from `frame.crop`, so a 21:9 look board makes a 21:9 film), **last-frame extend** (`createExtendChain`: extract frame → the model's image-to-video → join; `oss-extract-frame` on the open engine).
- **The request as asked** (round 5 part 1, W2). `createShotFilm`, `createKeyframeFilm`, `createExtendChain`, `createStillTo3d` and `createRelitClip` write the request they were given as `GenerationRequest.asked` on the first row they return (`withAsked`; a Fuobe Original keeps its engine), so a skill made from the result rebuilds one request, not the rows it expanded into. The API drops `asked` from input.
- **Face mosaic run** (`createMosaicRun`, round 5 part 1, O11). A Fuobe Soul request in a look with a step after it (PixeletedFace: `soulPostStep` is `face-mosaic`) becomes, for each picture (at most 4, each on seed + i), a two-step pipeline in one batch: the picture ("Before the face mosaic", marked `postMade` so it doesn't start another), then the face mosaic on the same engine (`faceMosaicStep`: `oss-face-mosaic` on the GPU, `sam-3-1-face-mask` in the cloud). The mosaics come first in the answer, so a pipeline's next step or a Canvas node takes the pixelated picture; a request that waits for earlier steps waits with its picture.
- **Keyframe film** (`createKeyframeFilm`): Frames mode on an open model whose `keyframes` route is `chained`. `createGenerations` hands a keyframes request on Wan 2.2 14B (or Lightning) to it: one `wan22-flf2v-14b` clip per pair of neighbouring frames, each as long as its gap in the workflow's frame steps (`planKeyframeClips`), then an image-to-video clip after the last frame when it isn't at the end, then a join. The whole request is previewed first, and clips already made are canceled when one fails. A chained route can't be a step that waits for another step's output: `createGenerations`, `previewChained` and Canvas's `describeNode` refuse it with one message (`chainedWaitMessage`).
- **Pieces and windows** (`src/lib/catalog/remove-object.ts`, shared by Remove object and Genjutsu): a long clip is cut into pieces each cloud model takes (`planCloudPieces`), or into frame-exact windows for the open graphs (`planWindows`, `planFrameCuts`; `VACE_WINDOW` is 4n+1 frames, up to 81). Each piece is trimmed and made, the pieces are joined, and the clip's own sound is put back (`joinWithSound`), with the helpers in `REMOVE_TOOLS` (fal trim / join / mux, or `oss-trim` / `oss-join-clips` / `oss-mux`). Open windows are joined with hard cuts; the seams have not been checked on real models.
- **Text to 3D on the open engine** (`createStillTo3d`, round 4 part 3): `oss-text-trellis2`'s `text-to-3d` route is `chained`. `createGenerations` reads the operation as the planner does (`inferOperation`, so Assist, MCP and API calls that leave `op` out get it too) and makes one batch of two steps: a Z-Image Turbo still (`oss-z-image-turbo`, 1:1 at 1K, the words plus "a single object … on a plain light grey background", feature `image-to-3d-step`, a helper the Library hides), then `oss-trellis2` on that still (`BUILDERS_3D`). A photo sent with the words is dropped. Like a keyframe film, it can't wait for another step's output: `chainedWaitMessage(name, op)` now has 3D wording, and Canvas refuses any chained route fed by another node before Run.
- **Relit clip** (`createRelitClip`, round 4 part 3): a Fuobe DoP relight effect run on its own model (`relightStep` in `generations.ts`) is one batch of two steps. "Relit start frame" runs the preset's `prestep` on the clip's engine (`oss-qwen-relight` on ComfyUI; `qwen-image-edit-2509-cloud` with the Relight LoRA on fal); "Relit clip" takes it as its start frame. `createGenerations` checks text to 3D first, then the relight. Since round 5 part 1 the step can carry its own `params` and `labels`, and its model may be an Original that runs on the clip's engine: DoP's Mixed Media effects draw "Start frame as <Look>" on Fuobe Mixed Media, then "<Look> clip" (see Fuobe Originals).
- **Canvas nodes made in steps, or once per table row** (round 4 part 3, `runCanvas` in `src/server/canvas.ts`): a node whose `NodeRequest` has `steps` (the Video concatenator) runs as one `createPipeline` whose last step holds its result (`NodeRun.out`; the steps before it have feature `canvas-step`). A node fed by a Table has `rows`: one step per filled row (`StepSource {node, row}`: a row of the next node waits for the same row), each row a result (`NodeRun.rows`). Each row has a signature (`NodeRun.rowSigs`); a row whose inputs didn't change and whose result is live is kept (`keptRow`), so a failed, trashed or added row runs and is billed alone, and a node that takes rows is signed by all its row ids (`depIdentity`), so a film joined from rows goes stale when one is redone. The concatenator's steps, per clip: on the cloud `trim-video` (when cut) → `scale-video` (cropped to the film's size) → for a muted or soundless clip `merge-audio-video` with a silent WAV the server writes when the run starts (`silenceRef`, `silenceWriter`; for a muted clip of unknown length `extract-soundtrack` → `ffmpeg-loudnorm` at −70 dB → the mux), then `join-clips` at 30 fps, folded in joins of up to 24; on the open engine `oss-fit-clip` (`video-fit-clip`: cut, framed, 30 fps, its sound or silence, in one streamed pass), then `oss-join-encoded`.

## LoRAs (`src/lib/catalog/loras.ts`, `src/server/loras.ts`)

Round 4 part 2. A run's LoRAs come from a preset's LoRAs (since round 4 part 3 on either engine: Fuobe DoP's map v2 in `oss-loras.generated.ts`, through `dop.ts`), a Fuobe Soul look (round 4 part 3: `LORA_LIBRARY` keys), a Mix, an @character's trained LoRA (since round 4 part 4 on every model of its family: see Training), the request's `loras` (API callers and the evaluation harness: at most 8), or, since round 4 part 4, a graph that loads its own (the H3 graphs' `graphLoras`). The library (`lora-library.generated.ts`) gives each researched file its pins and licence; a LoRA the library doesn't know is the user's own. Nothing is committed to the repo: files are fetched when a run needs them.

Since round 4 part 4 a LoRA's licence is information, not a gate (the owner's decision of 2026-10-27). A LoRA licensed for the user's GPU only (civitai without "Rent", `gpuOnlyLicence`) goes to fal or Replicate like any other, and the run's notes say what its licence says, unless Settings → Models & licences turns on "Keep them on your GPU" (under "LoRAs licensed for your GPU only"; `keepGpuOnlyLoras`): the server then marks the run's LoRAs `keepOnGpu`, and `localOnly` keeps those off the cloud. LoRAs switched off there, by file or by licence class, leave the run with their trigger words (`offeredLoras` in `src/server/model-access.ts`); the user's own LoRAs (no recorded licence, no library entry) are exempt from the class switches.

- **Open engine.** Before a ComfyUI run, `ensureLorasOnComfy` compares the run's LoRAs with ComfyUI's own list (`comfyLoraFiles`) and the LoRA folder. A missing file is downloaded into Settings → LoRAs folder (`comfyLorasDir`, `COMFYUI_LORAS_DIR`) by `downloadLora`: a Hugging Face file at its pinned commit, a civitai file by its pinned version with the user's civitai key (`?token=`, redacted from error messages). The bytes are hashed while they stream to a `.part` file and kept only when they match the SHA256 pinned in the library (else the one Hugging Face or civitai states). One download per file runs at a time (`downloadOnce`), and the job's card shows its progress ("Downloading … · 40%"). With no folder set, the run stops with what to do; a gated Hugging Face file has to be placed by hand. A trained Soul ID LoRA (round 4 part 4) is copied into the folder from Fuobe's own copy (`ownCopy`). `injectLoras` then adds the loader nodes.
- **Cloud engine.** `fitLoras` keeps what the route can carry: never a gated Hugging Face file or a file that exists only on ComfyUI, nor a GPU-only LoRA while the admin keeps those on the GPU (`localOnly`); over the API's maximum, the first ones win. A trained Soul ID LoRA (`LoraRef.own`) goes through `sendOwnLora`: the copy the trainer left on fal while it lives, else Fuobe's own copy (or the one in ComfyUI's folder) uploaded once, else the trainer's URL. A mirror is made again after 7 days on fal and 1 day on Replicate (guesses: neither documents how long uploads live). The civitai key is never sent to fal or Replicate. Files downloaded only to mirror them live in `<data dir>/loras` (`LORA_CACHE_DIR`).
- **Without a civitai key** (round 4 part 3). Before a Fuobe Soul run, `withoutUnreachableCivitai` (`src/server/loras.ts`) leaves out the civitai LoRAs the run can't get (not in ComfyUI's LoRA folder, or no live mirror for the cloud), takes their triggers off the front of the prompt (`promptWithLoras`) and adds a note; the look's words still carry it. On the open engine it only does this when the LoRA folder is set: without the folder, a missing file still stops the run. Any other run (a motion, whose LoRA is the point) still stops before the job.
- **Records.** Every copy, a download into ComfyUI's folder or a mirror, is a `lora_mirrors` row (file, target, source URL, version, hosted URL, SHA256, size and the licence / permission snapshot it was made under). Since round 4 part 4 a trained LoRA's copies are rows too (source `fuobe:<file>`, or the trainer's fal URL: `recordTrainedMirror`).
- **Settings → LoRAs** (`src/components/lora-settings.tsx`) reads `GET /api/loras`: the library with each file's licence line, whether it is in the folder, where it was mirrored, a `folderProblem` for a folder setting that can't be read, and whether a civitai key is set (never the key). `POST /api/loras {file}` downloads one library LoRA now (`downloadToComfy`). The civitai key's Save & test asks civitai's `/me` (`testCivitaiKey`).
- **Research pins.** `scripts/fetch-lora-pins.py` pins every LoRA of the research to exact bytes (SHA256, size, the Hugging Face commit), and `scripts/fetch-hosted-schemas.py` reads the hosted endpoints' input schemas (since round 4 part 4 also `--trainers` and `--base-only`); both need the network and aren't part of `gen:catalog`. `gen-lora-library.py` fails on a missing pin; since round 4 part 4 it prints a licence-rule break (a non-commercial LoRA in a default row) as a note instead of failing.
- **Recipe LoRAs** (round 5 part 1). A model whose recipe needs a LoRA (an Original, or `oss-tryon-klein`) lists it in `ModelOptions.loras` (the library's `adapter` group, all on by default): `planGeneration` puts it before the user's own, so on an API with a cap the user's give way first. `prepare()` refuses the run, naming the LoRA, when Settings → Models & licences has it switched off, or when the route leaves it out for another reason (the cap, a licence class, no cloud path; not checked in demo mode). `recipeLoraOff` (`src/server/model-access.ts`) makes such a model count as off, so pickers and server defaults move on (Fashion Factory's outfit to FASHN in the cloud or Qwen edit on the GPU when the try-on LoRA is off). ## LLM provider (`src/server/providers/llm.ts`)

Text steps (`translate`, `write`) run inside the server and are polled like any job; cancel aborts the call and a restart fails the job as "Interrupted" (retryable). `llmBackends(route)` lists the backends in order: Claude (claude-opus-5-5, low effort, server-side fallback) when an Anthropic key is set and Prompt enhancement is Claude, or Auto on an install that isn't open-only; then Ollama when it answers, unless Prompt enhancement is pinned to Claude. Claude errors fall back to the next backend; endpoint `ollama` (`oss-text-llm`) never uses Claude; Prompt enhancement → Offline rewriter (`none`) turns text steps off. Since round 4 an open-source **translation** with no Ollama answering runs on ComfyUI instead, when ComfyUI answers: `viaComfy()` submits and polls the hidden `oss-qwen35-translate` model (Qwen3.5 4B, workflow `translate-qwen35-textgen`) with the same numbered batches, one prompt at a time, so cues keep their timing; writing still needs Ollama, and the message with neither running names both. The first check for a new Ollama URL is a blocking worker-thread probe, later checks refresh a 15 s cache in the background. Since round 5 part 1 (fixes-5) Ollama's check (`probeOllama`, `GET /api/tags`) follows ComfyUI's busy-vs-down rules through `src/server/providers/reach.ts` (see Providers): a refused port or an HTTP error is down at once, a late answer is busy when Ollama answered in the last 2 minutes, else a port that takes a connection gets one 10 s look. The blocking first check (`probeOllamaSync`) counts a port that takes the connection but stays silent for 1.5 s as busy, so reachable, until the background check settles. Assist asks through `ollamaSoon`, which waits at most 1.5 s and only for what no check has said yet, and lists Ollama's models from the shared check (`ollamaModels`); before, Assist had its own 0.8 s check. The other awaited checks (an LLM chain step, Genjutsu's Describe, Evolution's direction, the Faceless writer) can now wait about 12 s the first time on a port that accepts connections but never answers. A text step on Ollama costs 0. The connection test asks the servers themselves: the Anthropic key with a free one-model list call (`testClaude`), Ollama with `/api/tags` and whether the model Settings names is pulled (`testOllama`).

`translateCues()` translates JSON cue lists, SRT and WebVTT (`src/lib/cues.ts`) in numbered batches of 30 (multi-line cues kept together); a batch that comes back merged or short is redone in pieces of 10, then cue by cue through a pool (1 request in flight on Ollama, 4 on Claude). The output keeps `meta.cues`. `write` uses `params.extra.system` when given. Studios that need free text (brand research, the AI Director, storyboard splitting, ad copy, Click to Ad scripts, Content Factory's cloud style brief) call `llmText()` in `src/server/enhance.ts`, with offline fallbacks. Faceless and Explainer names, topics and scripts, and Content Factory's episode titles, go through the llm provider itself (`askLlm()` in `src/server/faceless.ts` submits and polls a `text-llm` / `oss-text-llm` job), so they follow the episode's engine. The Explainer also reads PDF and Word sources (`POST /api/explainer/document`, up to 20 MB; `readDocument()` in `faceless.ts`): PDFs through Assist's unpdf reader, `.docx` through `src/server/assist/docx.ts` (`word/document.xml` via the bounded unzip, which skips entries it doesn't need); a document longer than the script writer reads is summarised by the engine's text model first. ## Live updates (`src/server/live.ts`, `src/lib/api.ts`)

Server: `watchGenerations(db)` installs TEMP SQLite triggers on `generations` that call a JS function (`fuobe_generation_changed`); changed ids are batched per event-loop turn (`setImmediate`) on an HMR-safe emitter (`globalThis.__fuobeLive`). The resolver in `generations.ts` turns each id into a `generation` event (the row through `toGeneration()`, the same JSON the list returns) or `deleted` (gone or trashed; trash and restore touch `updated_at`, so they fire too). `GET /api/generations/stream` (`generationEventStream`) sends `retry: 2000`, the events and `: ping` every 15 s, with `no-cache, no-transform` and `X-Accel-Buffering: no`; the listener is removed on abort.

Client: one stream per browser. Tabs elect a leader with `navigator.locks` (`fuobe-generation-stream`); only the leader reads the stream and re-broadcasts events and its connected state on a `BroadcastChannel` (`fuobe-generations`, messages event | state | hello). The next tab takes over when the leader closes; a tab hidden for 30 s lets go, and every reconnect after the first invalidates the caches. Without Web Locks each tab reads its own stream. State lives on `globalThis.__fuobeClientStream`; the decision logic (`streamResponse`, `needsCatchUp`, `toChannelMessage`) and the cache reducers are pure, in `src/lib/generation-stream.ts`. `applyEvent()` patches `["generations", filter]`, `["library", filter]`, `["assist", id]` and `["canvases", id]` (`applyToCanvasView`) by id, with id-based structural sharing (`shareById`). Other views subscribe with `useGenerationEvents(cb)` (Cinema, Layers, Shorts, Mixed Media, Marketing, Faceless, dub, Katana) instead of opening an EventSource. Polling slows to 10 s while connected (1.5 s otherwise); a 404 means no stream, retried every 5 minutes.

Notifications (round 4): `src/components/job-notifications.tsx`, with the decisions pure in `src/lib/job-watch.ts` and the per-browser opt-in in `src/lib/notification-prefs.ts` (Settings → Notifications). A job is a batch (a pipeline's steps count as one), and it counts as done only after it has stayed finished for 6 s, so steps a studio adds meanwhile belong to it. Only the stream's leader tab notifies, after asking the other tabs on the channel whether one is on screen. The tab title counts running jobs ("(2) Library · Fuobe").

## Library: Trash, folders, pins, review, bulk, zip (`src/server/library.ts`)

- **Trash** is the `generation_trash` table (soft delete). Every reader (`listGenerations`, `getGeneration(id, {includeDeleted})`, and through them Assist, MCP, storyboards, studios) leaves trashed rows out; `toGeneration` fills `deletedAt` / `folderId` even for rows read without the join. `trashGenerations` cancels queued and running jobs; `restoreGenerations` brings rows back (to the root when their folder is gone). `deleteForever` / `emptyTrash` call `deleteGeneration`, which removes the row, its trash and folder entries and every output file that `assetInUse()` doesn't find in a table listed in `ASSET_REFS` (in `generations.ts`: generations, elements, trainings, Assist chats with their frozen context and project sources, Cinema, Canvas, Layers with its tools' inputs, Shorts, marketing, image studios, Faceless channels and episodes with their scripts and plans, dub sessions, Katana jobs, since round 4 part 2 Content Factory series with their reference clip, since round 4 part 4 Assist's scheduled tasks with their files, and since round 5 part 1 skills' files, `skills.files_json`, moved from `ASSET_FREE`, so a file a skill's recipe names survives Empty trash; the match is by asset id anywhere in a skill's text files). Each entry also says what a row is and how to name it, so `assetUses()` can say where a file is used ("2 results and the element “Maya”"). `ASSET_FREE` lists columns that look like file columns but never hold one (round 4 part 2 adds `lora_mirrors`' source URL, hosted URL and licence: a LoRA's download and the provider's copy, never Fuobe's files; round 4 part 4 adds `shares`' tags and items, a scheduled task's rule and mode, and a connector's URL and tools); a test checks that every `_json`, `_url`, `url` and `_file` column is in one list or the other. When a table starts storing file URLs, add it there. `ensureTrashPurge()` empties what has been in the Trash for 30 days, at startup and then daily.
- **Folders**: `folders` + `folder_items`, one folder per generation. Since round 4 folders nest (`folders.parent_id`, up to `MAX_FOLDER_DEPTH` = 8 levels); names are unique among siblings, and a move into the folder itself or one of its subfolders is refused. Deleting a folder moves its results and subfolders up to its parent (to the root for a top-level folder). A folder's count and cover leave out the Trash and helper steps. `GET /api/folders/[id]/zip` zips a folder with its subfolders as paths (`?check=1` asks first, `?steps=1` adds helper steps).
- **Pins and review**: `pinned_at` on folders (pinned folders list first, in the order they were pinned) and on generations (`pinned=1` lists the most recently pinned first, with the cursor on the pin time; the Library shows them in a Pinned section) and `generations.review` (`in-progress`, `needs-review`, `approved`, `rejected`, or none), set through `PATCH /api/generations/[id]` (`pinned`, `review`) and the bulk route.
- **Helper steps**: a list that names no feature and no batch (the Library, the home feed, Assist's `list_recent`) leaves out chain steps (features ending in `-step`) and the helper features in `HELPER_FEATURES` (`src/lib/library.ts`; since round 4 part 2 also `eval`, the evaluation harness's jobs, and since round 5 part 1 `skill-check`, a skill check's dry run, whose rows also go to the Trash) unless `steps=1`; studio feeds that name their features still get them, and the facets count them apart.
- **Lists** take `kinds`, `models`, `statuses`, `since` / `until`, `folder` (or `folders`, a subtree), `trash`, `pinned`, `reviews`, `steps`, `q` (also the request prompt) and a compound cursor `before=<ts>:<id>` (ordered by ts DESC, id DESC; `deletedAt` in the Trash), so rows sharing a timestamp are never skipped. `libraryFacets()` gives the tab counts.
- **Bulk**: `POST /api/generations/bulk` (trash | restore | delete | favorite | unfavorite | move | pin | unpin | review), sent in batches of 500.
- **Zip**: `GET /api/generations/zip?ids=` streams a stored zip (`zipStream` / `zipSize` in `src/server/zip.ts`: a CRC pass first, flat memory, refused over 4 GB). `zipToFile` writes one to disk from files that arrive one at a time (EXR frames).
- **Uploads**: `DELETE /api/assets/[id]` deletes a stored file for good, its file on disk included, only when nothing uses it (`deleteUnusedAsset`); otherwise it answers 409 with where it is used. `GET` returns the uses.
- **Sharing** (round 4 part 4): a folder's menu and a finished result's menu share them by link, the selection bar publishes a selection, and the Shared tab lists the links (see Share links and Publish). A share names generations, folders or projects, never files, so it keeps no file alive, and a result moved to the Trash drops off its page (a shared result's link answers 404).
- Client: pure helpers in `src/lib/library.ts` (filters, date sections, batch stacks, `cursorAfter`, `toggleAll` for Select all and per-day select, `describeUses`), `outputActions()` in `src/lib/output-actions.ts` (one action list for tiles, viewer and Library; since round 5 part 1 every succeeded result that isn't an upload has "Make a skill from this…", and the Library's selection bar has "Make a skill": see Skills that run by themselves), `ForeverConfirmProvider` in `src/components/studio/result-actions.tsx`, and `components/library/{folders,review,upload-delete}.tsx` (folder tree with breadcrumbs and drag-and-drop, the review picker, the checked upload delete). `GenerationRequest.title` / `.batchTitle` (server-set) name results and Library stacks.

## Share links and Publish (`src/lib/share.ts`, `src/server/share-access.ts`, `src/server/shares.ts`)

Round 4 part 4. A share link is an unguessable token that opens one public, read-only page and the files that page shows, nothing else. It names a result, a Library folder (with its subfolders), a Cinema project or a published selection (`ShareKind`), never files, so the page shows what still exists.

- **Tokens** (`src/server/share-access.ts`). `newToken()` makes a 12-character id (the row's key, for the lookup) and a 32-character secret, base64url, 44 characters in all. Only the SHA-256 of the whole token is stored (`shares.token_hash`); `findShare` compares in constant time (against a dummy hash when the id is unknown) and refuses an expired link, and revoking deletes the row. The owner gets the token once, in the answer to `POST /api/shares`; the browser that made it keeps the URL in localStorage (`fuobe.shareLinks`), so only that browser can copy it again. `shareTargetExists` checks with one lookup that the result (succeeded, not in the Trash), folder or project is still there.
- **The proxy's share routes** (`openShare` in `src/proxy.ts`). After the host allowlist and the cross-site check, and before sign-in, a GET or HEAD on exactly `/s/<token>` or `/s/<token>/f/<path>` (`shareRoute`: a 44-character token, a stored path with no dot segments, at most 300 characters) passes without a session, password or not. An unknown, expired or revoked token, or a target that is gone, is rewritten to `/s/gone` with a 404. Wrong tokens count against `ShareGuard`: once per token per window; past a global budget of 100 a minute they get 429; only a client the server can tell apart (the last `X-Forwarded-For` hop with `FUOBE_TRUST_PROXY=1`) is locked out, for 60 s after 20 wrong tokens in a minute, its own working links included. Everyone else's live links keep opening, and the signed-in owner is never limited. Only the proxy decides what counts as a view (`countsAsView`: a browser's GET of the page, not a HEAD, a prefetch, an RSC request or a link-preview bot); it passes that on in the `x-fuobe-share-view` header, after deleting any copy the client sent, and the page records it (`recordView`). Share responses carry `X-Robots-Tag: noindex, nofollow, noarchive` and `Referrer-Policy: no-referrer`.
- **The share-scoped files route** (`src/app/s/[token]/f/[...path]/route.ts`) checks the token again and serves a stored file only while that share's page shows it (`shareServesFile`: the page's file set, cached until the next database write), with `Cache-Control: private, max-age=300`. It goes through `fileResponse` (`src/server/file-response.ts`, which `/api/files` now uses too) with `clean`: `src/server/media-clean.ts` blanks the generation data embedded in the file as it streams, without changing its size or any offset (PNG text chunks with ComfyUI's prompt and workflow, JPEG and WebP EXIF and XMP, MP4 / MOV and WebM / MKV tags, FLAC, MP3 and Ogg comments, GLB extras, SVG metadata), so byte ranges work as on the stored file. A file whose metadata area can't be read gets a 404 (it fails closed). Patches are cached per path, size and modified time (500 entries). The owner's own `/api/files` copy is untouched.
- **The public page** (`src/app/s/[token]/page.tsx` with `src/app/s/share-page.tsx`, outside the `(studio)` group so the page has one `<main>`; `src/app/s/gone/page.tsx` says "Link unavailable"). `buildPublicShare` builds what visitors see: the title, description and tags, the media at share-scoped URLs with each piece's model name, Download, and, with prompts shown, each prompt with "Recreate in your Fuobe" (which copies it). With prompts hidden, titles made from a prompt are replaced too. A result, folder or project shows as a grid (a folder or project its newest 200, `SCOPE_LIMIT`); a published page as Feature, Series or Carousel (up to 100 pieces, `MAX_PUBLISH_ITEMS`), with the cover placed by `orderForLayout` / `coverSlide` and used as the link preview's `og:image`. The page renders per request (`connection()`) and is never indexed.
- **Owner API and UI.** `GET` / `POST /api/shares` list the links (with a `signIn` flag) and make one; `GET` / `PATCH` / `DELETE /api/shares/[id]` read, change (title, description, tags, layout, `showPrompts`, `expiresInDays`, or `newLink: true` for a new token) and revoke. The API takes 1–365 days or no expiry; the dialog offers Always, 1, 7 or 30 days. `ShareProvider` (`src/components/share/share-provider.tsx`) wraps every studio page and loads the dialogs on first open: "Share link…" in a finished result's menu (`outputActions`' `share` item, only for files Fuobe stores), in a Library folder's menu and in a Cinema project's header and menu (`share-dialog.tsx`, which warns on `localhost` and when no password is set); Publish from the Library's selection bar (`publish-wizard.tsx`: Details, Assets, Cover, Access); and Library → Shared (`/library?tab=shared`, `shared-links.tsx`).
- **Storage.** Migration 19 adds `shares` (see Storage); `shares.tags_json` and `items_json` are in `ASSET_FREE`, so a share keeps no file alive.

Checked: unit tests (token storage and lookup, scopes, share-scoped files, the proxy's paths, `ShareGuard`, views, the cleaner over synthetic media) and a scripted live check against a dev server in demo mode with a password set and the visitor signed out, with real ComfyUI PNG and MP4 outputs in the data folder. Not checked: real fal or Replicate files through the cleaner. An MP4 track's handler name isn't blanked, and Canvas boards can't be shared.

## Security (`src/proxy.ts`, `src/server/auth.ts`, `src/server/remote-fetch.ts`)

- **Sign-in** is off until a password is set in Settings → Security or `FUOBE_PASSWORD`. State lives in `data/auth.json` (not SQLite) so the proxy can check requests with `fs` and `crypto` alone: a scrypt password hash, an HMAC secret for 30-day session cookies (replaced when the password changes), and API tokens stored as SHA-256 hashes. The proxy lets `/login` and `/api/auth/login` through (and, since round 4 part 4, GET and HEAD on a share link's page and files, checked by `openShare`: see Share links), answers other API calls with 401 and redirects pages to `/login?next=…` (`safeNext()` in `src/lib/safe-redirect.ts` keeps it on the same origin). Its matcher leaves out only build assets, `samples/` and root SVGs.
- **Host allowlist** (`hostAllowed`), for every method when no password is set, before anything else: IP literals, localhost and `*.localhost`, single-label names, `.local` / `.lan` / `.home.arpa` / `.internal` / `.localdomain`, this machine's hostname, and `FUOBE_ALLOWED_ORIGINS` (`*` allows any). This stops DNS rebinding. `X-Forwarded-Host` is not trusted here.
- **Cross-site writes** (`crossSite`): non-GET/HEAD/OPTIONS requests get 403 when `Origin` matches neither Host, `X-Forwarded-Host` nor `FUOBE_ALLOWED_ORIGINS`, when it is `null`, or when `Sec-Fetch-Site` is cross-site — with or without a password.
- **Login throttle** (`LoginGuard`): 5 misses per client and 20 a minute overall, bounded map, `Retry-After`. Route handlers can't see the socket address, so the client key is the last `X-Forwarded-For` hop only with `FUOBE_TRUST_PROXY=1` (then a 60 s lock per client); otherwise everyone shares a key that is slowed to one attempt every 4 s and never locked. Since round 4 part 4 the same client key drives `ShareGuard`, the throttle on wrong share tokens.
- **Remote fetch** (`fetchRemote`): every caller-supplied URL (references, brand research, product links, YouTube oEmbed, Assist sources) is fetched only from public addresses. The check runs inside the socket lookup (DNS can't change after it) and again on each of at most 5 redirects; it blocks loopback, RFC 1918, link-local / metadata, CGNAT, multicast, ULA and mapped / NAT64 / 6to4 IPv4. 60 s deadline, 200 MB cap. `fetchRemoteToFile` makes the same checks but streams to a file (16 GB cap, 30-minute deadline; a failed download leaves no file); it fetches the extra files a result links to. `FUOBE_ALLOW_PRIVATE_URLS=1` turns both off for LAN installs, and since round 4 part 4 also lets an Assist connector's URL use plain http beyond localhost (Fuobe never fetches a connector's URL itself: Anthropic's servers do).
- **LoRA links** (round 4 part 2) don't go through `fetchRemote`. `POST /api/generations` takes a LoRA link only over https on huggingface.co, hf.co, civitai.com, fal.media or replicate.delivery, with no credentials in it (`LORA_HOSTS`, since round 5 part 1 in `src/server/request-schema.ts` with the rest of the API's request schema, `GenerationRequestSchema`, which a skill's recipe goes through too; server-set fields such as `skill`, `demo` and `asked` aren't in it, so input drops them), and a file name that stays inside the LoRA folder (`lorasPath` also requires `.safetensors`). The server may download such a file into the LoRA folder before a ComfyUI run. Downloads from huggingface.co and civitai must match a SHA256; a link on hf.co, fal.media or replicate.delivery isn't held to one, so such a file can be kept unchecked, with no size limit and a 60-minute timeout. The civitai key travels only in civitai's download URL and is redacted from messages.
- **Connection tests** (`POST /api/providers/test`, `src/lib/connections.ts`): Settings' Save & test sends the typed, unsaved values; the route runs the provider's `test()` inside `withCandidates()` (an `AsyncLocalStorage` override of `getSetting`, `src/server/settings.ts`) and stores nothing. Testing a different, unsaved ComfyUI address doesn't send the saved token to it (`isCandidate` / `savedSetting`). Like saving an address, a test makes the server fetch the ComfyUI or Ollama address it is given. Since round 4 part 2 the route also tests the civitai key (`{provider: "civitai"}`, civitai's `/me`), which isn't a model provider's. Since round 4 part 5 `higgsfield` is no test provider: the route answers 400 "Unknown provider". Since round 5 part 1 (fixes-5) it tests AI-Toolkit (`{provider: "ai-toolkit"}`, `testAiToolkit` in `src/server/training.ts`): `GET <url>/api/jobs?only_active=true` with a 10 s timeout and the token when one is set, or, with `field: "aiToolkitDatasetDir"`, whether that full path (or its nearest existing parent) can be written, without creating it. A saved token isn't sent to a new, unsaved address. Like the others, this makes the server fetch any address typed in Settings.
- Uploads up to 200 MB pass the proxy (`experimental.proxyClientMaxBodySize: "210mb"` in `next.config.ts`, room for the multipart overhead). Since round 4 part 5 `POST /api/uploads` also takes MKV (`video/x-matroska`) and AVI (`video/x-msvideo`) for every upload (only Character Swap Studio's picker lists them; the others still list MP4, MOV and WebM), and maps the names browsers give them (`video/avi`, `video/msvideo`, `video/vnd.avi`, `video/mkv`); browsers can't play AVI, so only Character Swap Studio makes a playable copy (on the cloud), and some providers may refuse it. `/api/files` sends `nosniff` and a UTF-8 charset for text; since round 4 part 4 it and the share files route share `fileResponse` (`src/server/file-response.ts`), and a path that exists but isn't a file is a 404. The MCP endpoint refuses a foreign `Origin`. **Real 404s**: the proxy rewrites an unknown `/apps/<id>`, an unknown hub mode (`unknownHubMode`) and a record page whose id isn't stored (`recordForPath` in `src/lib/record-pages.ts`, then `recordExists` in `src/server/records.ts`, one primary-key lookup; a database that can't be read counts as "exists") to the not-found page with a 404, because a page's `loading.tsx` streams a 200 before the page knows. Every `[id]` page also calls `notFound()` (round 4 part 5 adds `/character-swap/[id]`, record kind `swap-project`).

## Assist agent (`src/server/assist/`)

A manual tool-use loop over Claude (adaptive thinking with `block_binding` drop-block, betas `thinking-binding-controls-2026-08-01` and `server-side-fallback-2026-07-01` (not for Haiku), and since round 4 part 4 `mcp-client-2025-11-20` when connectors ride along, top-level `cache_control` and two cached system blocks, streamed with `client.beta.messages.stream(...).finalMessage()`, `max_tokens` 32k or 64k at Extra / Max effort). Modes: **Free** (Ollama, or the offline planner), **Smart** (Claude, needs a key), **Manual** (pick claude-opus-5-5, claude-sonnet-5-5, claude-haiku-5-5 or claude-fable-5-1 and the effort). `resolveAgent()` picks one per chat.

- **Context.** Each chat's context (date, engine, approval mode, project, sources, memory, skills index, active skills) is built once and frozen in `assist_thread_state`; later changes arrive as role `system` "Context update" messages, saved only after a reply succeeds, so preserved thinking stays valid.
- **Tools** (`tools.ts`, `context-tools.ts`, `studio-tools.ts`): `search_models` (kinds image, video, audio, text, model3d; since round 4 part 3 it says an Original runs on both engines and names the 139 looks; since round 4 part 4 it lists only models Settings → Models & licences offers, and the offline planner's default picks fall back with `offeredDefault`), `list_elements` (since round 4 part 4 a trained element counts only LoRAs some run can use), `list_recent`, `check_generations` (text inline, meta, images attached), `generate` (with `after`: the call becomes one `createPipeline`; not `strict`, zod-validated; since round 4 part 3 a job takes `look` and `engine`, and a job without an engine follows the user's; since round 4 part 5 a job naming a retired model or operation runs on its replacement, `toRequest` through `currentRequest`, without the note), `create_storyboard` (the only `strict` tool; since round 5 part 1 each frame priced on its own model through `estimateStoryboard`), `list_skills`, `load_skill` (since round 5 part 1 a skill with a recipe also gets its "Run it" section, as the chat context's active skills do), `remember` (asks first), `read_source`, the studio tools `split_layers`, `restyle_footage`, `dub_video`, `faceless_episode`, `create_ads`, `add_captions`, and `katana`. Gated calls stop the loop with an approval card priced by `previewGeneration`; `PlannedJob.atomic` marks a pipeline's steps and `planRunnable()` keeps Run off while any step has an error. `answerApproval` claims the thread before its first await.
- **Studio tools** resolve through `STUDIO_ROUTES`, which `assist/studio-routes.ts` fills (since round 4) for `split_layers`, `restyle_footage`, `dub_video`, `faceless_episode`, `create_ads` and `add_captions`. Each adapter prices the job with the studio's own estimate and starts it through the studio's server module, so it opens as a Layers project, a Shorts session, a dub to review, a Faceless episode (in an "Assist" channel made once) or an Ads Studio batch, or in the Captions editor. Since round 4 part 5 `create_ads` always plans Fuobe's ads (copy and a visual, each in 1:1, 4:5 and 9:16), since round 5 part 1 with the visual on Fuobe Marketing Image; since then `restyle_footage`'s Shorts session runs `fuobe-shorts` by default on both engines. A call the studio can't take runs as a `createPipeline` of catalog models in the Library (for `restyle_footage` on the open engine, `fuobe-mixed-media` at seed 424242 with references dropped), and the card, the result and the chat say why. `planFor()` returns where the job opens (`JobPlace`: studio and page), for the approval card and MCP's `estimate_job`. Genjutsu, Character Swap Studio, Remove object, Content Factory, the AI Influencer builder, Evolution and Layers' Inpaint, Enhancer and Save as element have no Assist or MCP tool yet.
- History is stored append-only exactly as the API returned it; local images are kept as URLs and converted to base64 per request. Since round 5 part 1 (fixes-5) `resolveAgent()` and the panel ask Ollama through the shared busy-vs-down check (`ollamaSoon`, at most 1.5 s), so a busy Ollama no longer sends a chat to the offline planner (see LLM provider). The same loop runs on Ollama's tool calling, or with no LLM on a rule-based planner (still → animate, N-shot films, N takes numbered on their tiles and then "animate 2" for the one picked, translations, skill hints, "remember that…").
- **Scheduled tasks** (round 4 part 4; `src/lib/assist-schedule.ts`, `src/server/assist/schedules.ts`). A task is a prompt (with files, a project, an engine and the chat's mode) that runs as a new chat on the server's clock. Rules (`ScheduleRule`): daily at a time, weekly on some days, every N real hours (1–168), or once, in an IANA time zone. `nextRun` works out the next time with `zonedToUtc` / `wallClock`, pure, so the dialog's "Next run" preview and the server agree: a time a spring-forward skips runs as much later as the clocks jumped, a time a fall-back repeats runs once, and every N hours ignores the clocks. The sweep (`ensureScheduleRunner`, started at boot by `src/instrumentation.ts`, and when a task is made) runs every 30 s, the first one 5 s after boot, and starts up to 10 due tasks, each claimed by a compare-and-set on `next_run_at`, so two sweeps never start the same run and a run missed while the server was off happens once. A run time that passes while the previous run is still going is skipped and recorded, not queued. Every process on the same database sweeps, dev servers included. Each run is a new chat ("<task> · <time>") in the task's project; its context says it is a scheduled run nobody watches (`scheduleLine`), so the model doesn't ask questions and ends with a summary. **Approval modes:** Ask first (the default: the plan waits as an approval card, and nothing is generated until it is approved, though a Claude run still uses the Anthropic key to plan) or auto-run within a cap per run (`cap_usd`, default $2, at most $500): `step()` prices each gated call with `planFor()` and `spendOf` (demo jobs $0, an unknown price always waits), `withinCap` lets it start while the run's `spent_usd` stays under the cap, and a plan over it waits. Claude's own tokens and connector side effects aren't counted. `POST /api/assist/schedules/[id]/run` (Run now) answers 202 with the chat, 409 only while the last run is still going, 422 with the reason when paused or failed. Deleting a project pauses its tasks, with the reason shown (`deleteProject` in `assist/projects.ts`). The UI: the Schedule button in a chat's header, `/assist/scheduled` and each project's Scheduled tab.
- **Connectors** (round 4 part 4; `src/lib/assist-connectors.ts`, `src/server/assist/connectors.ts`). Custom remote MCP servers in Settings → Assist · connectors (`#assist-connectors`; `/api/assist/connectors[/id]`): name, URL, optional token and optional allowed tools. `checkConnectorUrl` takes https, plain http only for localhost unless `FUOBE_ALLOW_PRIVATE_URLS=1`, no user name or password in the URL, at most 2,048 characters, and warns that a local or private address needs a public tunnel. Tokens and URLs are stored in plain text in SQLite like the other keys; the browser gets them masked (`maskToken`, `maskConnectorUrl`: the query and every path segment that isn't a short plain word hidden). Claude chats send them through the Messages API's MCP connector (beta `mcp-client-2025-11-20` beside the others): `mcpParams` gives one `mcp_servers` entry (URL, slug, `authorization_token`) and one `mcp_toolset` per enabled connector, and an allow-list turns the rest off (`default_config: {enabled: false}` plus `configs`). Anthropic's servers connect and call the tools inside the reply, so approval cards and the cap never see those calls; the context's `connectorsLine` tells the model to check in chat before posting, sending, creating, editing or deleting in an Ask-first chat. Every ordinary Claude chat gets every enabled connector (`assist_thread_state.connectors` defaults to 1); a scheduled run only when its task opts in (`assist_schedules.connectors`, off by default). History from a connector deleted or switched off is sent as text (`withoutMissingServers`); the stored history is unchanged. Ollama and the offline planner can't use connectors and say so once. The transcript lists each connector tool Claude used.

## Skills that run by themselves (`src/lib/recipe.ts`, `src/server/recipes.ts`, `src/lib/recipe-builder.ts`, `src/server/recipe-builder.ts`)

Round 5 part 1 (Work2Skill W1 and W2; plan in `docs/research/work2skill-7.md`). `SKILL.md` stays the playbook people and agents read. A user skill "runs by itself" when its files hold a valid `recipe.json`: Fuobe checks it, prices it and runs it with new inputs, with no chat and no LLM. The recipe lives in the skill's existing `files_json`, so there is no migration.

- **The format** (`src/lib/recipe.ts`, pure and browser-safe; `RecipeSchema`, `fuobeRecipe: 1`). Typed inputs (`params`: image, video, audio, text, number, choice or @element; at most 12) and either a graph of `generate` steps (each a `GenerationRequest` with `after` and `chain`, exactly as `createPipeline` takes them; at most 24) or one `tool` step (a gated Assist tool such as `dub_video` or `add_captions`, alone). A string that is exactly `"{{id}}"` takes the input with its type; `{{id}}` inside a longer string inserts its text. Optional `checks` per step (kind, count, aspect, seconds, sound, and a `look` sentence for a model that sees images) and `verified` per engine (the day the plan check, the dry run and the real test passed, and `catalog`, a hash of each step's model, operation, route and price table). Server-set fields (`SERVER_FIELDS`: `skill`, `demo`, `asked`, `chainFilled`…) are stripped from a recipe's requests. `recipeProblems` refuses at save time, never at run time: unknown or unused placeholders, duplicate ids and keys, a tool step that isn't alone, a graph `createPipeline` would refuse, a count that varies on a step others wait for, and inputs whose default, example or options don't fit their type.
- **Fill and compile.** `fill` puts the values in (defaults for what isn't given). `compile` turns one run into the filled requests of one `createPipeline`, each stamped with `skill {name, run}` and the skill's title as `batchTitle` (a dry run adds `demo: true` and the hidden feature `skill-check`), or into one tool call. `checkValues` validates a row and `parseRows` a pasted or uploaded CSV / TSV (up to 50 rows), the same in the browser and on the server. `recipeMarkdown` writes the "Run it" section (inputs, steps, the equivalent `generate` or studio-tool call; at most 20,000 characters) that `load_skill`, the chat context and MCP prompts add to a recipe skill.
- **Runs on the server** (`src/server/recipes.ts`; routes under `src/app/api/assist/skills/[name]/` with `src/server/recipe-routes.ts`). `compileRun` sends every filled request through the API's own `GenerationRequestSchema` and puts a dual-engine Original on the run's engine. Fuobe never moves a step to the other engine: `recipeEngines` is the engines every step allows under Settings → Engine mode. `estimateRecipe` prices one run or many with `planSteps` / `planFor`, as Assist's approval card does. `runRecipe` starts one `createPipeline` per row, or one `executeTool` call per row whose rows `stampRequests` (`generations.ts`) stamps afterwards. A run is refused with 409 until the plan check has passed on that engine, or while the skill is switched off; a CSV with a header and no rows is a 422.
- **Checks** (`verifyRecipe`, `POST …/verify`). `plan`: each step planned and priced as it would start; when every refusal is only a provider to connect (`onlyConnect`: messages that start "Connect"), the same run on the demo route stands in, with a note. `demo` (the default): the plan check, then a free dry run on the mock provider whatever Settings → Demo mode says (`request.demo`; at most 120 s per engine; small stand-in files for media inputs with no example), whose hidden rows go to the Trash; a Run doesn't wait for it. `real` (API only, needs `confirm: true`, holds the request up to 15 minutes): the examples on the user's keys, outputs checked by their structure (`probeMedia`) and the look judged only by a model that sees images (`llmSeesImages`; on the GPU only Ollama, never paid Claude). Tool steps get the plan check only. `needsRecheck` asks for a check again when a step's model was retired (`REPLACED_BY`) or switched off, or the plan hash changed. A check that finds the recipe changed while it ran refuses with 409 and keeps the edit. An uploaded `recipe.json` loses its `verified` dates, and the .zip download (`?format=zip`) never carries this install's checks; examples and source stay out unless `&examples=1`.
- **Making a skill from results** (W2; `src/server/recipe-builder.ts`, `src/lib/recipe-builder.ts`, `src/components/skills/*`). `draftFromGenerations` walks the picked results back through `depends_on` and chain slots to the exact requests that made them. Results handed on by hand in the composer (Edit, Animate) are linked by matching file URLs (`linkByFile`); a stack that ran as one job per result becomes one step (`jobsOf`); an expansion comes back as the request it was asked as (`GenerationRequest.asked`; older ones are told apart by step labels and refused with `STEPS_REFUSAL`); a retired model moves to its replacement (`currentRequest`); and Translate & dub, Katana and Captions are lifted to their Assist tools (`dub_video`, `katana`, `add_captions`). Other studios that plan their own steps are refused by name (`STUDIOS`, `notSupported`). Every input starts Fixed. The review screen marks what varies (media, @elements, whole prompts, words picked in a prompt, and the takes, shape, length and quality), and `buildRecipe` and `skillBody` write the recipe and SKILL.md live. `POST /api/assist/skills/draft` returns the draft and the refusals; `/draft/check` runs the plan check and the dry run on an unsaved recipe (kept in memory by recipe hash, `draftKey`: 200 entries for 6 hours, so a restart loses a passed dry run); `/draft/name` is an optional naming pass by Claude or Ollama; `/draft/save` checks the plan again and saves, with 409 for a taken name and 422 for a failing plan. "draft" is a reserved skill name; a user skill already called that would have its GET, PATCH and DELETE routes shadowed by the POST-only draft route (read from the routing, not tested, and nothing renames it). A skill made from demo results says so in its Run form (`DEMO_NOTE`, `source.demo`) until a real test passes.
- **UI.** A recipe skill's card on the Skills page shows "Runs by itself", and its dialog shows where it was checked or why it needs a re-check (`skills-view.tsx`). The Run form (`run-skill-dialog.tsx`, `/assist/skills?run=<name>`) builds its fields from the inputs, offers only engines whose check passed, prices live, lists the steps (`plan-jobs.tsx`) and has a Many tab for CSV rows. ⌘K lists "Run <skill>…" (`skillEntries` in `src/lib/command-search.ts`). "Make a skill from this…" is in every finished result's ⋯ menu and "Make a skill" in the Library's selection bar; `SkillBuilderProvider` wraps `StudioChrome` (`app-sidebar.tsx`), so the viewer opened from ⌘K or a job notification has it too, and loads the review screen on first open.
- **Checked** in demo mode only: unit and API tests (`recipe`, `recipes`, `recipe-builder`) with Demo mode off and no keys, and the browser checks `skills-run` and `skills-builder`. No skill has run with a paid key or on a GPU, the naming pass and look judging have not met a live Claude or Ollama vision model, the three lifts are tested as drafts only, and the real check level has no button. The text agents read (the "Run it" section, a built skill's SKILL.md) mentions a `run_skill` MCP tool that comes with W3 and doesn't exist yet.

## Command line (`bin/`)

- **`new-models-7`**: Open-H3-Regenerate-2K (a rough 384p–768p video redrawn at 1080p–4K), WorldCast (a photo and a camera path made into a fly-around) and MOSS-Image Layout (a picture drawn from boxes you place; hosted on fal), as 11 packages. Nobody hosts Regenerate 2K or WorldCast, so under the hosted-only rule they are planned for the GPU only, and the note's hosted stand-in recipes don't apply.
- **`dbs-separation-7`**: DBS soundtrack separation (dialogue, music and effects; two small Apache-2.0 models), plan D1–D10. Nobody hosts DBS: the note's cloud route on fal's SAM Audio is a stand-in the owner has ruled out, so it is planned for the GPU only.
- **`work2skill-7`**: the Work2Skill verdict, the `recipe.json` format and plan W1–W7. W1 and W2 are built here; W3–W7 (skills run from Assist and MCP, schedules and the CLI, Canvas, suggestions, skills across studios) are plans.
- **`accounts-8`** (with `accounts-8-screens.md`): accounts in three modes (Personal, In-house studio, Platform), sign-in on the better-auth library, teams, roles and spending limits in Fuobe's code, and a workspace for all 43 tables and every route (192 when the note was written), as 57 packages. Today Fuobe has no accounts (see Security).
